# DWR (Direct Web Remoting) AJAX Integration (MyDelivery)

## Overview
DWR is used in MyDelivery to provide AJAX-enabled calls from client-side JavaScript directly to Spring-managed Java beans. This document explains how DWR is configured, common usage patterns, security considerations, and references to the `DWRConfigurerServlet` implementation found in the project.

## Purpose

This document captures how DWR (Direct Web Remoting) is used by the MyDelivery presentation layer to provide AJAX calls from client-side JS into server-side Spring/flow beans. It lists where configuration is found, the typical exposed beans and method signatures, client examples, security considerations and operational troubleshooting steps.

## How it Works
- `DWRConfigurerServlet` initializes the DWR `Servlet` context and registers beans that should be exposed as JavaScript functions.
- Once registered, clients can call methods on those beans via `RemoteBean.method(args, callback)` patterns.
- Callbacks receive either an exception or a result; client code must handle both.

## Server-side Considerations
- Methods exposed should be thread-safe and avoid long-running blocking operations.
- Prefer returning lightweight DTOs rather than heavy domain objects.

## Flow integration patterns

- Partial updates to Spring Web Flow scope: AJAX can call a backing bean method that updates `flowScope` or a conversation-scoped bean. Ensure the server-side bean is conversation-scoped or uses the flow execution key to maintain consistency across requests.
- For methods that must update the persistent model, prefer the service layer that performs transactions and enqueues any downstream JMS messages after commit.

## Security
- Only expose necessary beans/methods via DWR; follow least-privilege.
- Validate all inputs server-side; client-side validation is not sufficient.
- Protect DWR endpoints with existing authentication filters or session checks.
- Use CSRF tokens for state-changing operations if applicable.

## Security considerations

- CSRF: DWR requests are POSTs and may require CSRF tokens depending on framework version — verify if CSRF protection is enabled and ensure client code sends tokens.
- Authentication/Authorization: DWR uses the existing HTTP session. Ensure exported methods perform explicit authorization checks (server-side) and do not implicitly trust caller-supplied IDs.
- Input validation: Validate all incoming DTOs—DWR will deserialize JSON into objects; server must re-validate before use in domain logic.
- Allowed methods: Use DWR config to restrict exported methods or use annotation-based exposure carefully.

// ...
function DWRPhoneValidation() {}
DWRPhoneValidation.prototype = {
  phones: function(p0,p1,p2,p3,p4,p5,p6,p7,p8, callback) { /* client-side wrapper that posts to /dwr/call/plaincall/DWRPhoneValidation.phones.dwr */ }

// ...

And for `DWRRemote` you'll see `getAddressLookUps` with the same pattern.

## How to fetch the generated JS stubs locally (PowerShell)
1. Start the webapp locally (Tomcat/Jetty) and ensure app context path is root or `/mydelivery` depending on deployment.
2. Run the following PowerShell command to fetch the generated stub for `DWRRemote`:

$uri = 'http://localhost:8080/dwr/interface/DWRRemote.js'
Invoke-WebRequest -Uri $uri -OutFile .\DWRRemote.js -UseBasicParsing

And for `DWRPhoneValidation`:

$uri = 'http://localhost:8080/dwr/interface/DWRPhoneValidation.js'
Invoke-WebRequest -Uri $uri -OutFile .\DWRPhoneValidation.js -UseBasicParsing

Adjust host/port/context-path to your local server.

## Troubleshooting & operational notes

- Generated JS: Visit `/context/dwr/interface` or `/dwr/interface/*` in a running instance to see the generated client stubs and confirm exported bean names and method signatures.
- Runtime errors: DWR logs exceptions to the server log; enable DEBUG on `org.directwebremoting` for detailed converter/serialization traces.
- Session issues: If AJAX calls show missing flow state, confirm the flow execution key is propagated, and that session affinity is preserved in clustered environments.
- Network/timeout: Increase Ajax request timeout for known long-running validations and provide an operation id pattern to poll status.
