# ACV Services - Glossary & Terminology

**Purpose:** Define business domain, technical terms, acronyms, and industry-specific vocabulary used in Account Creation Validations platform.

---

## A

**Account Creation Validation (ACV)**
The business process of rapidly and securely onboarding new customers while ensuring regulatory compliance. Core function of the ACV platform.

**Applicant**
The individual or business entity requesting account opening. Data subject of all validations.

**API Connector Service**
Separate ACV microservice responsible for integrating with external provider APIs (government agencies, credit bureaus, OCR vendors). Acts as abstraction layer for provider-specific protocol differences.

**Asynchronous Processing**
Non-blocking validation workflows where results are polled or delivered via webhook callbacks rather than returned in request response. Allows long-running external API calls without client timeout.

**Azure Event Hubs**
Managed streaming service in Microsoft Azure used by ACV Services to publish validation events (IDENTITY_VERIFIED, RECORD_VALIDATED, etc.) for asynchronous downstream consumption.

**Azure Blob Storage**
Microsoft cloud file storage service used by Document Service to persist compliance certificates and by clients to upload documents for validation.

---

## B

**Backoff (Exponential)**
Retry strategy where delay between attempts increases exponentially (1s → 2s → 4s → 8s). Used by RetryService for failed external provider calls.

**BRN**
Business Registration Number. Government-issued identifier for registered businesses. Common validation record type.

**Bearer Token**
OAuth2 token format included in HTTP Authorization header: `Authorization: Bearer <token>`. Used by ACV Services for request authentication.

---

## C

**Cache**
Fast in-memory data store (Redis). ACV Services caches country configurations to avoid repeated database lookups and reduce latency.

**Circuit Breaker**
Fault tolerance pattern that temporarily stops calling a failing external provider to allow recovery. Auto-enabled after repeated timeouts/errors.

**Compliance Certificate**
Document (PDF) generated by Document Service after successful multi-stage validation, certifying that applicant has passed all required compliance checks.

**Country Code**
ISO 3166-1 alpha-2 code identifying a country (US, CA, GB, DE, etc.). Used to scope validation rules and document requirements.

**Country Configuration (Country Config)**
Set of validation rules, required documents, and business policies specific to a country stored in `CountryConfigEntity` and cached in Redis.

**Credential**
Authentication information (username/password, API key, OAuth2 client secret) used to authenticate with external providers. Managed centrally by ConnectionsManagerServiceImpl.

---

## D

**Data DTO (Data Transfer Object)**
Serializable Java class used for API request/response payloads. Examples: `ValidationRequest`, `ValidationResponse`, `WregRequest`.

**Document Type**
Classification of compliance document (PASSPORT, BUSINESS_REGISTRATION, TAX_CERTIFICATE, DRIVER_LICENSE, etc.).

**DocumentManagementService**
Interface (in acv-commons) for requesting document generation. Implemented by Document Service microservice.

---

## E

**Entity**
JPA-annotated Java class mapped to a PostgreSQL table. Examples: `ValidationRequestEntity`, `TransactionTrackerEntity`, `CountryEntity`.

**Event Hub (Azure Event Hubs)**
Azure managed service for high-throughput event streaming. ACV Services publishes ~10 distinct validation event types for downstream consumption.

**Event-Driven Architecture**
System design where components communicate primarily through asynchronous events rather than direct service-to-service calls.

**External Provider**
Third-party service providing specialized validation (government ID verification, credit bureau scores, OCR processing). Integrated via API Connector Service.

---

## F

**Fault Tolerance**
System capability to continue operating despite component failures. Achieved via circuit breakers, retries, and default fallbacks.

**Future (Java)**
Concurrent programming construct representing a computation that will complete at some point. Used by virtual threads to track parallel record validations.

---

## G

**Get/Acquire**
Retrieve OAuth2 token from Okta or fetch configuration from cache/database.

**Global Exception Handler**
Spring `@ControllerAdvice` component that catches application exceptions and formats them into standard error responses.

---

## H

**HLD (High-Level Design)**
Document describing system architecture, components, major design decisions, and technology choices. See [HLD.md](HLD.md).

**Helm**
Kubernetes package manager. ACV Services Helm charts in `helm-releases/` contain deployment configurations for dev/test/prod environments.

**HTTP Status Code**
Standard HTTP response code indicating request result:
- 200 OK — Request succeeded
- 202 Accepted — Request queued for async processing
- 400 Bad Request — Invalid input
- 401 Unauthorized — Missing/invalid JWT token
- 404 Not Found — Resource doesn't exist
- 429 Too Many Requests — Rate limit exceeded
- 500 Internal Server Error — Server-side error
- 502 Bad Gateway — External provider error

---

## I

**Identity Verification**
Validation stage confirming applicant identity via OTP or document cross-reference.

**OIDC (OpenID Connect)**
OAuth2-based protocol for authentication. Okta implements OIDC to provide JWT tokens to ACV Services.

**Okta**
Enterprise identity provider offering OAuth2/OIDC authentication. ACV Services validates all inbound JWT tokens against Okta issuer.

**OTP (One-Time Password)**
Temporary 6-digit code sent to applicant email/SMS for identity verification. Expires after 10 minutes.

**OCR (Optical Character Recognition)**
Technology extracting text/data from document images. ACV Services delegates OCR to external provider, stores results in validation history.

---

## J

**JPA (Java Persistence API)**
Java specification for object-relational mapping. Spring Data JPA is ACV Services' ORM framework.

**JWT (JSON Web Token)**
Stateless token format used by OAuth2. Okta issues JWTs; ACV Services validates signature and claims in each request.

---

## K

**Kubernetes**
Container orchestration platform. ACV Services deployed as Kubernetes pods with Helm charts defining resource limits, replicas, and networking.

**KYC (Know Your Customer)**
Regulatory compliance requirement to verify applicant identity and collect background information before account opening.

---

## L

**LLD (Low-Level Design)**
Document describing internal code structure, class relationships, data models, and implementation patterns. See [code-mapping.md](code-mapping.md).

---

## M

**Microservice**
Small, independently deployable service focused on single business capability. ACV platform has 8 microservices (ACV Services being the central hub).

**Multi-Stage Validation**
Sequential validation pipeline where applicant progresses through stages (IDENTITY_VERIFICATION → RECORD_VALIDATION → CREDIT_VALIDATION → COMPLETION).

**Multi-Tenancy**
System supporting multiple independent customers (e.g., different banks). ACV Services achieves via OAuth2 scoping by client/tenant ID.

---

## N

**Namespace (Kubernetes)**
Logical isolation within a Kubernetes cluster. ACV Services deployed in separate namespaces: `dev`, `test`, `prod`.

---## O

**OAuth2**
Industry-standard authorization protocol. Okta implements OAuth2 client credentials flow for inter-service authentication.

**Okta Token**
See "JWT". OAuth2 access token issued by Okta OIDC provider. Required in Authorization header for all ACV Services API calls.

---

## P

**Persistence Layer**
Database abstraction provided by Spring Data JPA repositories. Decouples business logic from SQL/JDBC details.

**PII (Personally Identifiable Information)**
Sensitive applicant data (name, SSN, email, phone). ACV Services masks PII in logs via PiiMaskingUtil.

**Polling**
Client-initiated status checks. For long-running validations returning 202 Accepted, clients poll `/v1/transaction/{transactionId}` every 30 seconds.

**PostgreSQL**
Open-source relational database. ACV Services persistence store for all transaction, configuration, and audit data.

**Provider**
External service providing specialized capability (government, credit bureau, OCR vendor).

---

## Q

**Query** (Database)
SQL SELECT statement executed against PostgreSQL. Repositories define `@Query` annotations for complex queries beyond standard CRUD.

---

## R

**Rate Limiting**
Request throttling protecting against abuse. ACV Services limits to 100 requests/minute per authenticated client.

**Record**
Individual item being validated. A single ValidationRequest can contain multiple records (e.g., IDENTITY document + BUSINESS_REGISTRATION + TAX_CERTIFICATE).

**Redis**
In-memory caching store. ACV Services caches country configurations with 24-hour TTL to reduce database load.

**Repository**
Spring Data JPA interface for CRUD data access. Examples: `ValidationRequestRepository`, `TransactionTrackerRepository`.

**REST (Representational State Transfer)**
Architecture pattern for HTTP APIs. ACV Services exposes RESTful endpoints on `/v1/*` paths.

**Retry Logic**
Automatic re-attempt of failed operations with exponential backoff. RetryServiceImpl manages polling and retry scheduling.

**Role Based Access Control (RBAC)**
Authorization mechanism where users have roles (admin, operator, read-only) with associated permissions.

---

## S

**Service (Business Logic)**
Application layer (below controllers, above repositories) implementing domain workflows. Examples: `StageValidationServiceImpl`, `ConfigurationServiceImpl`.

**Service Interface**
Abstract contract defining service methods without implementation. Enables dependency injection and testability. Examples: `ValidationTriggerService`, `EventHubService`.

**Session**
Authentication session maintained via JWT token. Expires after 1 hour; refreshed via `AuthTokenController`.

**Signature Validation**
Verification that digital signature on document is authentic (optional validation option).

**Span** (Distributed Tracing)
Unit of work in distributed tracing. Correlation IDs attached to all requests for end-to-end observability.

**Spring Boot**
Production-grade framework automating Spring configuration. ACV Services built on Spring Boot 3.3.1.

**Spring Data JPA**
Spring abstraction over Hibernate ORM. Provides Repository interface reducing boilerplate CRUD code.

**Spring Security**
Framework providing authentication/authorization. Configured to validate OAuth2 JWT tokens from Okta.

**SQL**
Structured Query Language for database operations. Repositories use JPA/Hibernate to generate SQL automatically.

**Stage** (Validation)
Logical step in multi-stage validation pipeline. Stages include IDENTITY_VERIFICATION, RECORD_VALIDATION, CREDIT_VALIDATION, COMPLETION.

**Stateless Service**
Service without client-specific state. Important for Kubernetes: pods can scale/restart without losing validity.

---

## T

**Tax Certificate**
Government-issued document certifying business tax compliance. Common ACV validation record type.

**Thymeleaf**
Server-side template engine used by Document Service to render compliance certificates. Supports multi-language templates.

**Timeout**
Maximum allowed time for operation to complete. External provider calls timeout after 30 seconds; overall transaction after 5 minutes.

**Token Expiration**
JWT validity period. Okta tokens expire 1 hour after issuance; clients refresh via `AuthTokenController`.

**Transaction**
Complete validation workflow from initial request through multi-stage validation to completion. Identified by unique `transactionId` (UUID).

**TransactionTracker**
Entity tracking transaction state progression through validation stages. Updated as each stage completes.

**TriggerValidation**
Entry point for bulk validation requests. `ValidationTriggerServiceImpl.triggerValidation()` groups requests and spawns async tasks.

---

## U

**UUID (Universally Unique Identifier)**
128-bit identifier ensuring uniqueness across all transactions. ACV Services generates random UUID per transaction for tracking.

---

## V

**Validation**
Process of verifying applicant data/documents against rules and external sources.

**Validation Engine**
Separate ACV microservice (`eai-3540813-validation-engine`) implementing specific business rule validation logic. Factory pattern routes records to appropriate validators.

**Validation Request**
Initial REST API request from client to begin validation workflow.

**Validation Response**
API response containing validation result status, details, and next steps.

**Virtual Thread (Java 21)**
Lightweight "green thread" managed by JVM, not OS. ACV Services spawns 1 virtual thread per record for parallel record validation. Reduces memory overhead vs. traditional threads.

**VPC (Virtual Private Cloud)**
Network isolation in cloud. Kubernetes cluster and databases deployed in private VPC; external providers accessed via proxy.

---

## W

**Webhook**
Optional client-configured HTTP endpoint. ACV Services POSTs validation completion notifications to webhook URL instead of requiring polling.

**WREG**
Multi-record compliance document submission format. `WregRequest` DTO contains array of document records per applicant.

---

## X

**XML**
Legacy data format (sometimes used by government providers). ResponseTransformer handles XML↔JSON conversion.

---

## Y

**YAML**
Human-readable configuration format. Helm charts and `application*.yml` files written in YAML.

---

## Z

**Zuora**
(Not used in ACV; placeholder for future billing integration)

## Business Domain Concepts

### Compliance Validation Stages

1. **Identity Verification** — Confirm applicant identity via OTP or document cross-reference
2. **Record Validation** — Verify compliance documents (business registration, tax certificates)
3. **Credit Validation** — Optional credit bureau checks
4. **Result Aggregation** — Compile all validation results into final compliance determination
5. **Certificate Generation** — Generate PDF certification of compliance

### Validation Status Values

| Status | Meaning |
|--------|---------|
| PENDING | Waiting to be processed |
| IN_PROGRESS | Currently validating |
| PASSED | Validation succeeded |
| CONDITIONAL_PASS | Passed with warnings/exceptions |
| FAILED | Validation failed; does not meet requirements |
| RETRY_NEEDED | Transient error; will retry automatically |
| EXPIRED | Transaction expired; must restart |

### Document Types

| Type | Description | Validation Method |
|------|-------------|--------------------|
| PASSPORT | Travel document with applicant photo | OCR + Government lookup |
| NATIONAL_ID | National identification card | OCR + Government lookup |
| DRIVER_LICENSE | Driver license with address | OCR + Government lookup |
| BUSINESS_REGISTRATION | Business entity registration cert | OCR + Government lookup |
| TAX_CERTIFICATE | Tax compliance proof | OCR + Government lookup |
| UTILITY_BILL | Proof of residence | OCR only (address extraction) |

## Technical Patterns Used

### Design Patterns

| Pattern | Usage | Benefit |
|---------|-------|---------|
| **Facade** | `ConnectionsManagerServiceImpl` hides provider routing complexity | Simplifies external integration |
| **Factory** | `GenericValidationServiceImpl` dispatches to correct validator | Extensible validation types |
| **Strategy** | Different validation strategies per stage | Flexible validation pipelines |
| **Builder** | `ValidationResponseBuilder` fluent construction | Clean API response creation |
| **Singleton** | `ConfigurationService` (cached, Spring bean) | Single source of config truth |
| **Circuit Breaker** | Retry logic with failure threshold | Fault tolerance for external calls |

### Architectural Patterns

| Pattern | Implementation | Purpose |
|---------|----------------|---------|
| **Microservices** | ACV Services is hub; calls other ACV microservices | Scalability; independent deployment |
| **Event-Driven** | Events published to Event Hubs for downstream consumption | Loose coupling; asynchronous processing |
| **Request-Response** | REST API synchronous for immediate validations | Real-time user feedback |
| **Async Processing** | 202 Accepted + polling for long-running operations | Non-blocking for heavyweight validations |
