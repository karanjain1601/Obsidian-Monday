# DevOps & Platform Engineering: Introduction to All Topics

This document is a guided tour of the 7 sections in the DevOps & Platform Engineering knowledge base — a production-focused reference for engineers who take code from a laptop commit all the way to a monitored, self-healing production deployment. The content targets staff-level and platform engineers, and covers the full continuous-delivery lifecycle: version control, CI/CD pipelines, containers, Kubernetes orchestration, Infrastructure as Code, the three major clouds, and production observability.

**Suggested learning path:** Git & Version Control → CI/CD Pipelines → Containers & Docker → Kubernetes → Infrastructure as Code → Cloud Platforms → Monitoring & Observability

---

## 01. Git & Version Control

Git is the source of truth the entire delivery lifecycle hangs off — pipelines trigger on it, GitOps deploys from it, code review scales on it. This section builds the model from the object layer up to monorepo scale.

**What's covered:**
- **Git Internals** — Git as a content-addressable Merkle DAG of four object types (blob = file bytes, tree = directory listing, commit = full tree snapshot + parents, tag); the object id is the SHA-1 (migrating to SHA-256) of type ‖ length ‖ NUL ‖ content → automatic dedup and tamper-evident history; a commit stores a snapshot, not a diff; a branch is a 41-byte ref file and HEAD is a pointer; plumbing (`hash-object`, `cat-file`, `write-tree`) vs porcelain; packfiles delta-compress similar objects (default chain depth 50) so `count-objects` disk usage ≪ the sum of full object sizes; the reflog holds "lost" commits until `git gc --prune` expires them past the ~2-week grace.
- **Branching Strategies** — the real cost of a branch is integration lead time, and conflict surface grows ∝ p·(λt); GitFlow (`main` + `develop` + `release/*` + `hotfix/*`) for versioned/scheduled products; GitHub Flow (deployable `main` + short PR branches) for continuous web deploys; trunk-based development (sub-day branches + feature flags) is what makes CI genuinely continuous; rebase local/unpushed work, `merge --no-ff` shared branches.
- **Rebasing & Interactive History** — merge preserves true branching history, rebase *copies* commits onto a new base (new hashes, because a commit id depends on its parent) for a linear, bisectable line; interactive rebase verbs `pick`/`reword`/`edit`/`squash`/`fixup`/`drop` plus `--autosquash`; `cherry-pick` to back-port isolated fixes; `git bisect` finds a regression in ≈⌈log₂ n⌉ tests (1000 commits → ~10) and automates via `git bisect run`; recover with the reflog, publish rewrites with `--force-with-lease`, never plain `--force`.
- **Hooks & Automation** — client-side hooks (`pre-commit`, `commit-msg`, `pre-push`) and server-side hooks (`pre-receive`, `update`, `post-receive`); Husky to manage hooks and commitlint to enforce Conventional Commits; the pattern is shift-left enforcement — lint, format, and message checks before code ever reaches CI.
- **Monorepo Tools** — scale CI by computing the *affected subset* (the reverse-reachable closure over the dependency graph) and reusing cached outputs (hit ratio H = 1 − |affected|/|all|); Nx (inferred graph, content-addressed computation cache, `nx affected`, Nx Cloud), Turborepo (declarative `turbo.json` with `^build` deps and remote cache computed-once-globally), Bazel (explicit `BUILD` files, hermetic sandboxed reproducible builds); `git sparse-checkout` + partial clone and `git worktree` tame disk; CODEOWNERS automates review routing.

**Key mental models:** A commit is an immutable snapshot in a Merkle DAG, not a diff; branch cost is integration lead time, so keep branches short-lived; never rewrite or force-push public history (use `--force-with-lease`); at scale, only rebuild the affected subset and cache everything else.

## 02. CI/CD Pipelines

A well-designed pipeline catches regressions in minutes, packages one immutable artifact, and ships to production with instant rollback. This section covers the principles, the tooling, and the deployment strategies that make fast, safe delivery possible.

**What's covered:**
- **CI/CD Principles & Patterns** — CI (integration confidence), CD (every commit releasable), and Continuous Deployment (auto-promote every green commit) are three distinct guarantees; trunk-based development + feature flags; shift-left testing exploits the ~10× cost growth per escaped stage via the test pyramid (fast lint+unit gate under ~3 min, slow integration/E2E after); build-once-promote-everywhere by SHA-256 digest, never `:latest`, for an idempotent pipeline; pipeline-as-code; the DORA four keys pair throughput (deploy frequency, lead time) with stability (MTTR, change failure rate) — elite = on-demand deploys, <1h lead, <1h MTTR, 0–15% CFR.
- **GitHub Actions** — hierarchy event → workflow → jobs → steps; jobs run in parallel on isolated ephemeral runners (share nothing), steps run sequentially sharing a filesystem; core events `push`/`pull_request`/`schedule`/`workflow_dispatch`; hosted (ephemeral, reproducible) vs self-hosted (GPU, private VPC) runners; secrets masked at runtime, environments layer approvals + branch rules + scoped secrets; composite actions package repeated *steps* inline, reusable workflows package repeated *jobs*; `needs:` builds a DAG that executes in waves; the matrix strategy expands multiplicatively (3 OS × 3 versions = 9 jobs).
- **Jenkins & GitLab CI** — Jenkinsfile (declarative vs scripted) and shared libraries; GitLab CI stages/rules/needs, GitLab runners, parallel jobs, artifacts & caching — the enterprise, self-hosted end of pipeline-as-code.
- **ArgoCD & GitOps** — Git as the single source of truth, with a controller continuously reconciling cluster state toward the repo (pull-based deploy vs push-based CI); the ArgoCD `Application` CRD, sync waves & hooks, ApplicationSets, the app-of-apps pattern, and Flux as the alternative.
- **Release Strategies** — deployment (placing bytes) ≠ release (directing traffic); rolling updates (`maxSurge`/`maxUnavailable`, cheap but coarse), blue-green (atomic 100% flip, instant rollback, 2× infra), and canary (step traffic up gated by a rollback threshold θ on the traffic-blended error rate E = (p·e_c + (100−p)·e_s)/100); Argo Rollouts encodes the canary schedule with metric-gated `analysis` steps (Prometheus/Datadog); feature flags (LaunchDarkly/OpenFeature) push control into code for per-user releases and dark launches.

**Key mental models:** CI, CD, and Continuous Deployment are three different guarantees; build one immutable artifact and promote the exact bytes by digest; elite delivery wins on throughput *and* stability at once (they do not trade off); separate deploy from release so a bad version hits a small blast radius with instant rollback.

## 03. Containers & Docker

A container is not a lightweight VM — it is an ordinary Linux process wearing kernel-enforced blinders. Understanding namespaces, cgroups, and the layer cache is the prerequisite for effective Kubernetes operation.

**What's covered:**
- **Docker Architecture & Internals** — a container = a Linux process constrained by *namespaces* (what it can see) and *cgroups* (what it can use), with no guest kernel; the runtime chain `dockerd` → `containerd` → `shim` → `runc`, where the shim keeps containers alive across daemon restarts; six namespaces (`pid`, `net`, `mnt`, `uts`, `ipc`, `user` — the last maps container-root to an unprivileged host UID); cgroups v2's unified hierarchy caps CPU as a quota/period (`--cpus=0.5` → 50ms per 100ms) and memory as a hard limit enforced by the OOM killer; overlay2 stacks read-only image layers under one writable layer with copy-on-write; the OCI image/runtime/distribution specs make images portable.
- **Dockerfile Best Practices** — a Dockerfile is a cache spec: a layer is reused only if it and every prior layer are unchanged, so order least- to most-frequently-changed (`COPY` manifest → `RUN` install → `COPY` source); multi-stage builds compile in a discarded builder and `COPY --from` only the artifact (often 80–90% smaller, e.g. ~1200MB → ~180MB with distroless); the base-image ladder ubuntu/debian (70–120MB) → alpine (~7MB) → distroless (~2–20MB, no shell) → scratch (0MB); `.dockerignore` keeps `node_modules`/`.git`/secrets out; `ARG` (build-time) vs `ENV` (runtime), never secrets in `ARG` (use BuildKit `--secret`); `HEALTHCHECK` for real liveness.
- **Docker Compose & Networking** — Compose v3 YAML (services, `depends_on` + health checks); bridge/host/overlay network modes; DNS-based service discovery by service name; volumes (bind mount vs named volume vs tmpfs) — the multi-container local-dev and single-host orchestration layer.
- **Container Registry & Distribution** — the OCI distribution spec; Docker Hub vs ECR vs GCR vs GHCR vs Harbor; tag immutably by digest (`sha256:…`) and avoid the `:latest` anti-pattern; content trust/Notary, image pull policies, and layer deduplication across images.
- **Container Security & Hardening** — a shared kernel means hardening = removing escalation rungs; run as a non-root UID with `no-new-privileges`; read-only rootfs + a small tmpfs; `--cap-drop=ALL` (never grant `CAP_SYS_ADMIN`); keep the default seccomp profile (never `unconfined`) and layer AppArmor/SELinux; scan with Trivy/Grype and lint with Hadolint in CI; sign SBOM/SLSA provenance (syft + cosign); security is multiplicative — residual risk = R₀ × ∏(1 − mᵢ), so stack controls for defense in depth.

**Key mental models:** A container is a process with kernel-enforced isolation, not a VM; order Dockerfile instructions by change frequency and go multi-stage to ship only what runs; pin images by digest, never `:latest`; harden by stacking independent controls (non-root, read-only, cap-drop, seccomp) because risk compounds multiplicatively.

## 04. Kubernetes

Kubernetes is a declarative control system — you submit desired state and controllers reconcile reality toward it. Master the reconciliation mindset rather than memorizing `kubectl` verbs, and it becomes a predictable state machine.

**What's covered:**
- **Core Concepts** — declarative reconciliation; the Pod (shared net/storage namespace, one IP) is the scheduling atom, governed by `restartPolicy` plus liveness/readiness/startup probes (a failing liveness restarts with back-off capped at 5 min, readiness gates traffic without killing); a Deployment creates a new ReplicaSet per template change → zero-downtime `RollingUpdate` (`maxSurge` caps pods above desired, `maxUnavailable` below — they cannot both be 0) and instant `rollout undo`; ConfigMap vs Secret (base64 is encoding, not encryption → enable etcd encryption / external secret operators); Namespaces scope RBAC (ServiceAccount → RoleBinding → Role/ClusterRole) and cost controls (LimitRange per-object, ResourceQuota per-namespace); always set `requests` (scheduling) and `limits` (enforcement).
- **Networking & Ingress** — the flat-network contract (every Pod a routable IP, no NAT) implemented by a CNI (Flannel VXLAN overlay, Calico BGP L3, Cilium eBPF); a Service is a stable ClusterIP over readiness-filtered endpoints; kube-proxy in iptables mode (O(n) probabilistic rules) or IPVS mode (O(1) real round-robin) balances L4 *connections*, so a long-lived gRPC/HTTP2 stream pins to one Pod; types layer up ClusterIP → NodePort → LoadBalancer → ExternalName; CoreDNS resolves `<svc>.<ns>.svc.cluster.local` and headless Services give StatefulSets per-Pod records; Ingress consolidates HTTP/TLS behind one controller (nginx/Traefik/ALB); NetworkPolicy is a CNI-enforced allow-list; the Gateway API is the successor.
- **Storage & StatefulSets** — the PV/PVC lifecycle, StorageClass + dynamic provisioning; StatefulSet ordered deployment and stable network IDs (`web-0`, `web-1`) for stateful workloads; volume modes (Filesystem vs Block); CSI drivers; backup strategies; PodDisruptionBudget for HA during eviction.
- **Helm Charts** — package templated manifests + `values.yaml` into a versioned chart (`Chart.yaml` distinguishes chart `version` from app `appVersion`); Go templating with `.Values`/`.Release`/`.Chart` scopes and helpers (`default`, `toYaml | nindent`, `include`, `required`); rendering is a *pure* values → manifests function (`helm template`, diff-able and CI-testable with no cluster contact); every release is a stored revision, so `helm rollback` re-applies a known-good snapshot instantly; `--atomic` + `upgrade --install` for safe idempotent deploys; Helmfile for multi-release, OCI registries for charts, `ct` for lint/install-testing.
- **Operators & CRDs** — a CRD extends the API with a new kind validated by an OpenAPI v3 schema at admission; the `status` subresource enforces spec (desired, user-owned) vs status (actual, controller-owned); an Operator is a controller whose `Reconcile` loop is idempotent and *level-triggered* (acts on current state, requeues with back-off) so missed/duplicate events never corrupt convergence; Kubebuilder / Operator SDK scaffold the controller-runtime plumbing; conversion webhooks enable multi-version schema evolution and leader election (a Lease) keeps exactly one replica active; OLM/OperatorHub distribute; Prometheus Operator and Strimzi Kafka show the pattern at scale.

**Key mental models:** Everything is declarative reconciliation — controllers loop observe → diff → act toward desired state; always set resource requests/limits and readiness/liveness probes; reconciliation is level-triggered, so it self-heals regardless of event history; Secrets are only base64-encoded, so encrypt etcd and prefer external secret stores.

## 05. Infrastructure as Code

IaC treats provisioning and configuration as software engineering — version-controlled, peer-reviewed, testable, repeatable. This section spans the declarative (Terraform, CloudFormation) and imperative (Pulumi, Ansible) ends of the spectrum, plus drift detection and state management.

**What's covered:**
- **Terraform Core & Modules** — one loop: read config (desired) → read state (current) → diff → apply; HCL blocks/arguments where every reference builds an implicit DAG walked in topological order; plan symbols `+` create, `~` update, `-/+` replace, `−` destroy (reviewing that column in CI is the single highest-leverage safety habit); a remote backend from day one (S3 storage + DynamoDB lock + encryption, since state holds plaintext secrets); modules for reuse and blast-radius boundaries (pin versions); prefer `for_each` (stable, key-addressed) over `count` (fragile, index-addressed); `lifecycle` (`prevent_destroy`, `create_before_destroy`, `ignore_changes`) and sparing `depends_on`; workspaces and Terragrunt for DRY multi-environment setups.
- **CloudFormation & CDK** — CloudFormation stack anatomy (Resources/Parameters/Outputs/Mappings/Conditions), change sets + stack policies, nested stacks & StackSets; AWS CDK L1/L2/L3 constructs synthesizing down to CloudFormation, plus CDK Pipelines; the CDK-vs-Terraform trade-off (a real programming language vs cloud-agnostic HCL).
- **Ansible** — agentless configuration management over SSH that configures what lives *inside* hosts (packages, files, services), complementing a provisioner like Terraform; inventory (static/dynamic) → playbook → plays → tasks, with facts gathered up front and handlers that run once at the end, only on change; idempotency comes from declaring desired state (`state: present`) → `changed` on the first run, `ok` thereafter; Jinja2 templating; roles (`defaults`/`vars`/`tasks`/`handlers`/`templates`) shared via Galaxy; guard raw `command`/`shell` with `creates`/`changed_when`, lint with `ansible-lint`, scale with AWX/Tower.
- **Pulumi** — IaC in general-purpose languages (TypeScript/Python/Go), so loops, types, and unit tests are native; the Pulumi stack + state, `ComponentResource` for reusable abstractions, `pulumi up/preview/destroy`, and Pulumi ESC for environments/secrets/config; Crosswalk for AWS.
- **Drift Detection & State Management** — state is the ledger IaC diffs against, and drift (the ledger-vs-reality gap) makes the next routine `apply` unpredictable; `terraform plan` already refreshes to detect drift, `plan -detailed-exitcode` (exit 2 = changes) is a CI drift gate, and `plan/apply -refresh-only` reconciles state surgically; adopt out-of-band resources with the TF 1.5+ declarative `import` block (Terraformer for bulk reverse-engineering, Driftctl to find unmanaged resources); every drift has two valid resolutions (revert via `apply`, or accept via code/`import`); immutable infrastructure prevents drift from forming at all.

**Key mental models:** IaC is a diff-and-converge loop over config, state, and reality — review the plan's destroy/replace lines before every apply; state is the ledger and holds secrets, so use a locking, encrypted remote backend and keep it small per-layer; prefer `for_each` over `count` and pin module versions; never leave drift unreconciled, and prefer immutable infrastructure so drift cannot form.

## 06. Cloud Platforms

The three hyperscalers are a small set of primitives (compute, storage, network, IAM) plus hundreds of recombinations. This section covers each provider's core services, multi-cloud design patterns, and FinOps for cost governance.

**What's covered:**
- **AWS Core Services** — four primitives compose everything: EC2 (instance family + size, AMIs, placement groups cluster/spread/partition, ASG target-tracking that scales the count by M_current/M_target), S3 (11-nines object store across ≥3 AZs, the storage-class ladder + lifecycle policies as the biggest cost win, presigned URLs, S3 Select), VPC (a public subnet routes `0.0.0.0/0` → IGW, a private subnet egresses via a NAT Gateway, peering/PrivateLink), and IAM (deny-by-default, explicit `Deny` always wins, permission boundaries cap the maximum, roles + STS over static keys — instance profiles / IRSA / OIDC); Lambda runs on Firecracker micro-VMs where the cold start is the init phase (hoist SDK/DB setup outside the handler, use provisioned concurrency, bill by GB-seconds); managed ECS/EKS/Fargate, RDS/Aurora, and ElastiCache.
- **GCP Services** — GKE Autopilot (bill per pod request, no node ops) vs Standard (node control for GPUs/DaemonSets); Cloud Run scales on concurrency and to zero (instances = ⌈arrival-rate × latency / concurrency⌉, so raising concurrency is the top cost lever); BigQuery separates storage from *slots* — partition by your time filter and cluster (≤4 columns) to cut bytes scanned, with materialized views transparently substituted; Cloud Spanner delivers external consistency via TrueTime (GPS + atomic clocks) by commit-waiting out the uncertainty ε ≈ a few ms; Pub/Sub → Dataflow (Apache Beam) → BigQuery → Vertex AI composes a fully serverless data/AI pipeline, with Cloud Armor at the edge.
- **Azure Services** — AKS managed clusters; Azure Functions with Durable Functions orchestration; Azure DevOps (Boards/Repos/Pipelines/Artifacts); Azure AD → Entra ID identity; Blob Storage & ADLS Gen2; Azure OpenAI Service; Cost Management.
- **Multi-Cloud Patterns** — active-active (every region serves live, instant reroute, but needs headroom everywhere) vs active-passive (cheaper, pays a detection + promotion delay); redundancy gives availability A = 1 − (1 − p)ⁿ (two 99% regions → 99.99%), but correlated failure through a shared DNS/IAM/config path caps real availability at the least-independent shared component; Anthos and Azure Arc project one control plane over clusters across clouds/on-prem, with GitOps as the delivery mechanism; cloud-agnostic networking (SD-WAN, Cloud WAN / Virtual WAN); data sovereignty and vendor lock-in treated as a deliberate spectrum (open standards vs proprietary managed leverage).
- **FinOps & Cost Optimization** — manage on unit economics (cost per transaction / active user / 1000 requests) and treat a *rising* unit cost as the architecture warning sign; the four pricing models trade commitment/reliability for discount — On-Demand, Reserved (~40% at 1yr, break-even utilization u* = 1 − discount, i.e. 60% at a 40% discount), Savings Plans (~30%, flexible across families), and Spot (70–90% off but reclaimable in ~2 min, only for interruption-tolerant/checkpointed/diversified work); rightsizing via Compute Optimizer removes the most common waste, and scheduling non-prod off nights/weekends cuts its bill ~⅔; governance = consistent tagging → showback (visibility) or chargeback (accountability), with the FOCUS standard normalizing multi-cloud billing; budgets (alert at 80%/100%) + anomaly detection turn a surprise bill into a same-day incident.

**Key mental models:** Master the four AWS primitives (EC2 / S3 / VPC / IAM) and the rest of the catalogue is recombination; IAM is deny-by-default with explicit-deny-wins; the biggest discount is not automatically the cheapest — an unfilled Reserved commitment costs more than On-Demand; manage cost on falling unit economics, and remember multi-cloud resilience is capped by your least-independent shared dependency.

## 07. Monitoring & Observability

Observability is the ability to understand a system's internal state from its external outputs. The three pillars — metrics, logs, and traces — let you detect, diagnose, and remediate incidents, and SLOs turn raw signals into reliability commitments that drive engineering priorities.

**What's covered:**
- **Prometheus & Alertmanager** — a pull-based dimensional TSDB where a series = metric name + label set, so every distinct label value is a *new* series (bound cardinality — never put user IDs or ID-bearing paths in labels); four metric types over float64 (Counter via `rate()`/`increase()`, Gauge raw, Histogram via `histogram_quantile()`, Summary read directly); `rate()` needs a range vector, averages the per-second slope, and corrects counter resets — never use `delta()` on a counter or `rate()` on a gauge; service discovery + relabeling keep targets current; recording rules precompute heavy aggregations (`level:metric:operation` naming); alerting rules add a `for` duration to debounce pending → firing; Alertmanager deduplicates/groups/routes/inhibits/silences (page → PagerDuty, the rest → Slack).
- **Grafana Dashboards & Alerting** — Grafana queries, it does not store; a panel binds a query on a data source to a visualization (time series / stat / heatmap / table / logs), and the data-source plugin decouples panels from the backend (Prometheus/Thanos/Mimir); template variables (`$job`, `$__rate_interval`) make one dashboard reusable and zoom-aware; never graph *average* latency — compute percentiles from histogram buckets with `histogram_quantile`, aggregating `by (le)` before the quantile; Unified Alerting (query → reduce → threshold) spans data sources; dashboard-as-code with Grafonnet + Grizzly; Loki (label-indexed logs, LogQL) collected via Grafana Alloy or Prometheus Agent mode.
- **ELK/EFK Stack** — Elasticsearch index anatomy (shards/replicas/mappings); the Logstash pipeline (input → filter → output); Filebeat/Fluentd/Fluent Bit for collection (the F in EFK); Kibana Discover & Lens; index lifecycle management (ILM) hot → warm → cold → delete to control storage cost; Vector as a modern alternative shipper.
- **Distributed Tracing** — a trace is a tree of timed spans linked by a shared trace id and parent references, and the waterfall shows where a request's latency actually went; context propagation via the W3C `traceparent` header (version-traceid-parentid-flags, low flag bit = sampled) is what makes cross-service traces possible — the classic break is a Kafka/SQS async boundary where nobody injects the header; OpenTelemetry auto-instruments common libraries and provides a vendor-neutral SDK, with the Collector fanning out to backends; Jaeger (indexed storage) vs Grafana Tempo (indexes only the trace id, keeps spans in cheap object storage, searched with TraceQL); head sampling keeps a blind fraction p, tail sampling buffers and keeps by outcome (errors/slow); stamp the trace id into logs and metric exemplars to pivot across all three pillars.
- **SLO/SLI/SLA & Error Budgets** — SLI (measured good ÷ valid events) → SLO (target over a rolling 28-day window) → SLA (looser external contract with penalties), defined in that order; each extra nine roughly 10×s cost and slashes allowed downtime (99.9% = 40.3 min / 28d, 99.99% = 4.03 min) — pick the loosest target users tolerate; error budget = (1 − SLO) × window; burn rate = observed error rate ÷ (1 − SLO), where a rate of 1 exhausts the budget in exactly one window and 14.4× burns 2% of it in 1h; alert with multi-window, multi-burn-rate rules (short window fires fast, long window confirms and de-flaps); cap toil (<50% of an SRE's time) and encode an error-budget policy that freezes feature launches once the budget is spent (Google SRE-aligned).

**Key mental models:** The three pillars are metrics (that/what), logs (details), and traces (where) — correlate them by trace id in one investigation; never alert on averages — alert on symptoms and SLO burn rate, computed from histogram percentiles; `rate()` corrects counter resets and `delta()` does not; the error budget converts "is it reliable enough?" from an argument into arithmetic.

## Cross-Cutting Mental Models

These principles thread through every section and are the recurring themes of production platform engineering.

1. **Declarative, reconciled desired state** — From Terraform's plan/apply loop to Kubernetes controllers to ArgoCD GitOps, the dominant pattern is: declare the desired end state and let a controller diff it against reality and converge. Idempotent, level-triggered reconciliation is what makes the whole stack self-healing and reviewable.

2. **Immutability and content addressing** — Git objects, container image digests, and build-once-promote-everywhere artifacts are all identified by the hash of their contents. Pin by digest, never by mutable tag; immutable infrastructure leaves drift nowhere to accumulate. The same idea delivers deduplication, reproducibility, and instant rollback.

3. **Shift left and shrink blast radius** — Catch problems as early and as locally as possible: a bug caught by a pre-commit hook costs seconds, the same bug in production costs an incident. Small PRs, per-layer state files, per-environment accounts, canary slices, `cap-drop`, and least-privilege IAM all bound how far any single failure can propagate.

4. **Measure it or you cannot manage it** — DORA four keys for delivery, SLOs and error budgets for reliability, unit economics for cost. Each converts a vague argument ("fast enough? reliable enough? too expensive?") into a number with a target, and each drives a concrete action — split the pipeline, freeze features, or rightsize.

5. **Layered defense and independence** — Security is multiplicative (stack non-root + read-only + cap-drop + seccomp), and availability multiplies only when failure domains are genuinely independent — redundancy is capped by the least-independent shared dependency (DNS, IAM, a config push). Assume any single layer can fail and design so the next one holds.
