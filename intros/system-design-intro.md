# System Design & Engineering: Introduction to All Topics

This document is a guided tour of the 10 sections in the System Design & Engineering knowledge base — a production-focused reference for engineers designing, building, and operating large-scale systems and preparing for design reviews and interviews. The content targets senior and staff-level engineers and covers the full stack, from low-level OS primitives up through distributed architecture, security, observability, delivery practices, and emerging runtimes.

**Suggested learning path:** Foundations → Networking → Databases → Distributed Systems → Architecture → Infrastructure → Security → Observability → Practices → Advanced

---

## 01. Foundations

Every architectural decision eventually reduces to a foundational primitive — a cache miss is a data-structure question, a deadlock is an OS scheduling question, a God Object is a design-principles violation, a slow API is often an algorithm-complexity problem. Master these and the rest of the stack becomes pattern-matching.

**What's covered:**
- **Design principles** — KISS, DRY (Rule of Three; knowledge not code), YAGNI; SOLID (SRP = one reason to change, OCP, LSP, ISP, DIP); GRASP (Information Expert + Low Coupling + High Cohesion drive most decisions); Separation of Concerns; Dependency Injection / IoC (constructor injection preferred, makes unit tests trivial); Law of Demeter ("only talk to immediate friends" → avoid train wrecks).
- **Design patterns** — GoF creational (Singleton, Factory Method, Abstract Factory, Builder, Prototype), structural (Adapter, Decorator, Proxy, Facade, Composite), behavioral (Strategy, Observer/EventBus, Command, State, Chain of Responsibility); plus architectural patterns Strangler Fig, CQRS, Event Sourcing, Saga (orchestration vs choreography), and Outbox (the dual-write fix).
- **OS fundamentals** — process vs thread (isolated vs shared address space; fork/exec/wait, copy-on-write, zombies); memory layout (stack ~8MB, heap, virtual memory, page faults); signals (SIGTERM catchable → graceful shutdown vs SIGKILL uncatchable); file descriptors (EMFILE, ulimit -n); blocking vs non-blocking I/O, epoll/io_uring, the C10K problem (thread-per-conn → event loop).
- **Data structures & algorithms** — Big-O ladder O(1) → O(log n) → O(n) → O(n log n) → O(n²) → O(2ⁿ) → O(n!) with size heuristics (n ≤ 10⁴ → O(n²) ok, n ≤ 10⁶ → O(n log n)); arrays, hash maps, heaps, tries, BSTs (AVL/Red-Black), graphs (BFS/DFS, topological sort); sorting (merge/quick/heap/tim); DP, two-pointers/sliding window, union-find, binary search on the answer.

**Key mental models:** Complexity is the enemy of correctness — apply KISS and YAGNI as the counterweights to premature abstraction. Patterns are shared vocabulary, not rules: always know "what problem does it solve" and "when would I NOT use it." Use processes for isolation, threads for shared-state concurrency, and an event loop for many concurrent I/O waits. Start with brute force, state its complexity, then improve.

## 02. Networking

From a URL in the browser to bytes on the wire — networking underpins performance (latency ≈ distance ÷ speed-of-light), security (TLS everywhere), and API design (the protocol shapes everything above it).

**What's covered:**
- **Networking fundamentals** — DNS resolution flow (recursive resolver → root → TLD → authoritative), record types (A/AAAA/CNAME/MX/TXT/NS/SOA/PTR/SRV), TTL tuning before a migration; OSI 7 layers (engineers mostly reason at L4/L7); TCP 3-way handshake (~1.5 RTT to first byte → why keep-alive/pooling matters), reliability/ordering/flow/congestion control (CUBIC, BBR); UDP (connectionless — DNS, video, QUIC); latency vs bandwidth (NYC↔London ≈ 70ms floor); forward vs reverse proxy; NAT (SNAT/DNAT); stateful firewalls / NSGs.
- **HTTP & web protocols** — HTTP/1.1 → HTTP/2 (binary framing, multiplexing, HPACK) → HTTP/3 (QUIC over UDP, no TCP head-of-line blocking, 0-RTT); TLS 1.3 (1-RTT handshake, mandatory forward secrecy), cert chain of trust; method safe/idempotent matrix; status codes (401 = unauthenticated vs 403 = unauthorized); cookie flags (HttpOnly → XSS, Secure, SameSite → CSRF); CORS (simple vs preflight OPTIONS); WebSockets (101 upgrade, full-duplex) vs SSE vs long-polling; HTTP caching (Cache-Control, ETag, 304).
- **API design** — REST constraints (stateless, uniform interface, HATEOAS; Richardson Maturity L0–L3); versioning (URI vs header vs media-type); offset vs cursor/keyset pagination (O(offset) degrades vs O(1) constant); GraphQL (client-specified fields; N+1 problem → DataLoader batching); gRPC (Protobuf binary, HTTP/2, 4 streaming modes, for internal low-latency services); OpenAPI/Swagger; RFC 7807 Problem Details errors.

**Key mental models:** Latency × sequential calls is the core argument for parallelism, batching, caching, and HTTP/2 — chatty inter-region hops multiply RTT by the hop count. TCP vs UDP is a correctness-vs-speed trade, always stated with a specific use case. Reach for REST on public/CRUD, GraphQL for flexible many-client querying, gRPC for internal service-to-service throughput.

## 03. Databases

Choosing and using a data store correctly is one of the highest-leverage decisions in system design. The golden rule: start relational, add NoSQL only for a specific, proven access pattern.

**What's covered:**
- **Relational & NoSQL** — SQL (fixed schema, joins, referential integrity, normalization) vs NoSQL models (document, key-value, wide-column, graph, time-series) with polyglot persistence; ACID (atomicity/consistency/isolation/durability) vs BASE (basically available, soft state, eventual consistency); CAP (P non-negotiable → choose C or A during a partition; CP = etcd/ZooKeeper/HBase, AP = Cassandra/DynamoDB/DNS, tunable per-query in Cassandra) and its PACELC extension; join types INNER/LEFT/RIGHT/FULL (the LEFT JOIN … WHERE right.id IS NULL unmatched-row trick; Cartesian-product pitfall).
- **Transactions & indexing** — WAL for durability + replication; isolation levels and the three anomalies (dirty / non-repeatable / phantom reads; Read Committed is the Postgres default, Serializable = SSI); B-tree indexes (high branching, O(log n), range scans via doubly-linked leaves); composite-index leftmost-prefix rule (equality columns first, then range/sort); covering / index-only scans (INCLUDE); GIN/GiST/hash/partial index types; EXPLAIN ANALYZE (Seq Scan on a big table = missing index; sargability); connection pooling (PgBouncer transaction mode; pool_size ≈ cores × 2 + spindles).
- **Scaling databases** — vertical first, then horizontal; replication (leader-follower, sync vs async, read-your-writes anomaly under replication lag); multi-leader + write-conflict resolution (LWW / CRDTs); sharding (shard-key choice; range / hash / consistent-hashing / directory / geo — consistent hashing moves only ~1/N keys; hotspots, hard cross-shard joins); zero-downtime migrations (expand → backfill in batches → contract; CREATE INDEX CONCURRENTLY; never edit an applied migration); caching layer (cache-aside, write-through/behind/around, TTL, invalidation); CQRS at the data layer (CDC/Debezium → Kafka → denormalized read store).

**Key mental models:** Replication copies the *same* data (availability + read scaling); sharding splits *different* data (write + storage scaling) — large systems do both, and each shard is itself replicated. Exhaust query tuning, indexes, pooling, caching, and read replicas before sharding — it is a permanent complexity commitment. Cache invalidation and the read-your-writes anomaly are the recurring correctness traps of any read-scaling layer.

## 04. Distributed Systems

Distributed systems are fundamentally about managing failure, latency, and state across machines that cannot trust each other to be alive, fast, or in sync — never forget the 8 Fallacies (the network is *not* reliable, latency is *not* zero, topology *does* change).

**What's covered:**
- **Concurrency & async** — concurrency vs parallelism vs asynchrony; I/O-bound (async/event loop) vs CPU-bound (multiprocessing / real cores); cooperative scheduling (no data races *between* awaits) vs preemptive threads; epoll/kqueue/IOCP; the GIL (CPython threads give no CPU parallelism); OS vs green threads/goroutines (~1–8MB vs ~2–8KB stacks → millions of tasks); sync primitives (mutex, RLock, semaphore, condition variable with the spurious-wakeup while-loop, monitor); deadlock (4 Coffman conditions → break circular wait via global lock ordering), livelock, starvation; race conditions/data races, TOCTOU; optimistic (version column) vs pessimistic (SELECT … FOR UPDATE) locking; the actor model (no shared state, "let it crash"); thread-pool sizing.
- **Distributed concepts** — 2PC (prepare/commit; the coordinator-crash blocking problem → why sagas win) vs Saga (compensating forward transactions; orchestration vs choreography); idempotency keys + dedup table (at-least-once + idempotent consumer = effectively-once); Outbox pattern (dual-write fix via relay/CDC); vector clocks (track causality; incomparable = concurrent = conflict) with LWW/merge/CRDT resolution; CRDTs (G-Counter, PN-Counter, OR-Set, LWW-Register — commutative + associative + idempotent merge → converges); CAP + PACELC; Raft consensus (randomized election timeouts 150–300ms, terms, log replication, quorum = 2f+1); eventual-consistency mechanisms (read repair, hinted handoff, Merkle anti-entropy).

**Key mental models:** Almost every distributed pattern (Saga, CQRS, Outbox, idempotency keys, consensus) is a structured answer to one of three problems — failure, latency, or state. Async wins for thousands of concurrent I/O waits; the actor model trades locks for message passing. True end-to-end exactly-once is impractical, so engineer for at-least-once delivery + idempotent consumers. Quorum sizing 2f+1 with odd node counts maximizes fault tolerance while avoiding split-brain.

## 05. Architecture

How to design large systems — from the big-picture structure (monolith vs microservices, bounded contexts) down to the quality attributes (availability nines, RTO/RPO) that justify every structural decision.

**What's covered:**
- **Architecture patterns** — monolith vs microservices trade-offs (in-process ns vs network ms, blast radius, Conway's Law → start with a modular monolith) and the distributed-monolith anti-pattern; the interview framework (clarify → back-of-envelope estimate → API + data model → high-level design → deep-dive → bottlenecks → trade-offs); caching (stampede/thundering-herd fixes — mutex single-flight, probabilistic early expiry, stale-while-revalidate; penetration, hot keys); load balancing (L4 vs L7; round-robin / least-connections / consistent-hashing); rate limiting (token bucket for bursts vs leaky bucket for constant output vs sliding window; Redis Lua); API gateway / BFF; event-driven + Kafka vs RabbitMQ (log/offset/replay vs broker/queue routing); circuit breaker (Closed → Open → Half-Open) with timeouts, retries + backoff + jitter, bulkheads; service mesh (Envoy sidecar, mTLS); backpressure (bounded queues, pull, load shedding).
- **Domain-driven design** — strategic (ubiquitous language, bounded context, context map: ACL / conformist / customer-supplier / published-language) vs tactical (entities with identity vs immutable value objects; aggregates); aggregate rules (one transaction = one aggregate, reference by ID, root enforces invariants, keep small); past-tense domain events; repositories (one per aggregate root); CQRS + Event Sourcing (append-only events, snapshots, upcasters); core vs supporting vs generic subdomains.
- **Non-functional requirements** — every NFR = a number with a condition; latency in percentiles not averages (p99 dominates fan-out); Little's Law (L = λW); Amdahl's Law; availability nines (99.9% ≈ 43min/month, 99.99% ≈ 4.38min/month) and composite availability (0.999 × 0.999 = 99.8%); SLI/SLO/SLA + error budget (1 − SLO); reliability (Availability = MTBF ÷ (MTBF + MTTR)); DR (RTO = downtime vs RPO = data loss; backup / pilot-light / warm / hot-standby); CIA-triad security, maintainability (DORA metrics), observability, compliance (GDPR/HIPAA/SOC2/PCI), capacity planning (50–70% headroom).

**Key mental models:** Drive every design requirements → numbers → justified trade-offs, tying each choice back to the NFRs set up front — naming trade-offs explicitly is what signals seniority. Split into services only for team autonomy, independent scaling, or genuinely separate bounded contexts; never prematurely. The hardest, most important DDD decision is the aggregate boundary: "what must be immediately consistent in one transaction?" Each additional nine of availability is exponentially more expensive — set the target by business need.

## 06. Infrastructure

How to package, deploy, and run software reliably — the goal is to make releasing boring: small, frequent, automated, reversible changes.

**What's covered:**
- **Containers & Kubernetes** — containers virtualize the OS (namespaces isolate visibility, cgroups limit resources) vs VMs virtualizing hardware; Dockerfile layer caching (copy manifest before source — once a layer busts, every layer after rebuilds), multi-stage builds + distroless (~300MB → ~5MB), never :latest; Compose; K8s control plane (API server, etcd, scheduler, controller-manager) + kubelet/kube-proxy; core objects (Pod → ReplicaSet → Deployment; Service ClusterIP/NodePort/LoadBalancer; ConfigMap/Secret; Ingress); liveness (restart) vs readiness (de-route, no restart) probes; requests vs limits (OOMKill, CPU throttle); rolling update (maxUnavailable 0, maxSurge 1); Helm charts.
- **CI/CD & delivery** — CI (merge frequently, mainline always green, fail-fast pipeline < 10min); trunk-based (with feature flags) vs GitFlow; semver + lockfiles (npm ci, not install); Continuous Delivery (manual gate) vs Deployment (fully automatic); rolling vs blue-green (instant rollback, 2× infra) vs canary (1% → 5% → 25% → 100%, limits blast radius); feature flags (decouple deploy from release, kill switch); build-once-promote-everywhere immutable artifacts; DORA metrics; GitOps (Git = source of truth, pull-based reconciliation via Argo CD/Flux, git revert = rollback).
- **Cloud & platform engineering** — AWS/Azure/GCP service equivalents; IaaS/PaaS/SaaS/FaaS + shared-responsibility model (you always own your data); object storage (eleven-nines durability, storage classes, lifecycle policies, presigned URLs); VPC/subnets/security-groups/NAT (public the minimum, private by default); serverless cold starts + mitigations (provisioned concurrency); FinOps pricing (on-demand / reserved / spot, surprise egress cost); IaC/Terraform (declarative HCL, remote state + locking, plan before apply, never hand-edit state); platform engineering (IDP, golden paths / paved roads, Backstage, cognitive-load reduction, platform-as-product).

**Key mental models:** Namespaces isolate what a process can *see*; cgroups limit what it can *use* — no guest OS, no hypervisor. Liveness failure restarts, readiness failure only de-routes — confusing the two is a classic outage. Build the artifact once and promote the exact same bits dev → staging → prod. GitOps flips push → pull so CI never holds production credentials and the cluster continuously self-heals against drift.

## 07. Security

Security is a property of how you build the whole system, not a feature bolted on at the end — think defense-in-depth, least privilege, and assume breach.

**What's covered:**
- **Application security** — OWASP Top 10 (Broken Access Control #1 → enforce authz server-side on every request, deny by default; Injection; Cryptographic Failures); XSS (stored / reflected / DOM → output encoding, textContent not innerHTML, CSP, HttpOnly); CSRF (SameSite cookies + synchronizer tokens; bearer-header auth is largely immune); SQL injection (parameterized queries are the only real fix); AuthN ("who are you") vs AuthZ ("what may you do"), RBAC vs ABAC; password storage (salt + deliberately slow hash: Argon2id / bcrypt cost ≈ 12 / scrypt / PBKDF2 — never MD5/SHA-256); JWT (header.payload.signature, Base64 not encrypted → pin the alg, block alg:none/confusion; short access + revocable refresh tokens); OAuth 2.0 (authorization; Auth Code + PKCE) vs OIDC (authentication/SSO, ID token); symmetric vs asymmetric (hybrid TLS); hashing (integrity) vs encryption (confidentiality); secrets management (never in Git/images; Vault/Secrets Manager, rotate, least privilege); STRIDE threat modeling.
- **Zero trust & supply chain** — castle-and-moat fails (lateral movement, VPN over-grants) → "never trust, always verify" per request (identity + device posture + context; Google BeyondCorp); least privilege, micro-segmentation, short-lived auto-rotated credentials, OIDC federation (no static cloud keys); workload identity SPIFFE/SPIRE (SPIFFE ID URI, X.509-SVID, attestation solves "secret zero"); mTLS (both sides authenticated) via service mesh; supply-chain lessons (SolarWinds = build compromise; Log4Shell = invisible transitive dep); SBOM (SPDX/CycloneDX), provenance, typosquatting/dependency-confusion defenses; SLSA levels 0–3; Sigstore keyless signing (Cosign/Fulcio/Rekor transparency log); admission policy (Kyverno/OPA) verifying signatures before deploy.

**Key mental models:** Network location is not a credential — verify identity + context on every request, not once at a perimeter. Parameterized queries, SameSite cookies, and pinned JWT algorithms are the specific non-negotiable fixes for the three most common web attacks. Signing proves integrity only *since signing* — combine it with build integrity (SLSA) and an SBOM, because a compromised build signs the malware too. Credential danger ≈ value × lifetime × scope, and shortening lifetime is the easiest big win.

## 08. Observability

You can't improve what you can't measure. Observability turns running systems from black boxes into machines you can ask *arbitrary* questions of at runtime — the prerequisite for low MTTR.

**What's covered:**
- **Observability & monitoring** — monitoring (known failure modes) vs observability (explore unknown failures); the three pillars — logs (structured JSON + trace_id), metrics (counter / gauge / histogram → percentiles not averages), traces (spans + parent-span tree); the workflow metric alert → dashboard → trace → logs; W3C traceparent correlation ID; Prometheus pull model + PromQL + Grafana + Alertmanager (beware high-cardinality labels like user_id); RED (Rate/Errors/Duration) for services, USE (Utilization/Saturation/Errors) for resources; symptom-based actionable alerts, alert fatigue, runbooks, blameless postmortems; SLI/SLO/SLA + error budgets (govern velocity vs reliability, burn-rate alerts); distributed tracing (context propagation; head vs tail sampling — keep errors/slow); OpenTelemetry (instrument once → Collector fans out to any backend).
- **Performance profiling** — measure first, the bottleneck is never where you think (Knuth); sampling (low-overhead, prod-safe: perf, py-spy, pprof) vs instrumentation (exact, high-overhead: cProfile); the profile → hypothesis → ONE change → re-measure loop; Amdahl's Law + the 90/10 rule; flame graphs (width = time, wide top plateaus = hot leaves, self vs total time, differential/off-CPU variants); memory (heap snapshots, retained size, dominator tree, leak = unintentional retention, GC pressure → allocate less); I/O profiling (slow queries via EXPLAIN ANALYZE; the N+1 problem → join/batch/IN; chatty APIs → batch/parallelize); benchmarking pitfalls (JIT warmup, dead-code elimination/Blackhole, constant folding, report p50/p95/p99, realistic data); latency-budget breakdown; k6/JMeter/Gatling/Locust.

**Key mental models:** Metrics alert you → dashboards scope it → traces pinpoint the slow hop → logs explain the root cause. Averages lie for latency — always report p99 (a 100-call fan-out almost always hits the tail). Optimize only the profiled hot 10%; Amdahl caps a 1%-of-time win at ~1%. The most effective memory fix is "allocate less," not "tune the GC harder." Instrument once with OpenTelemetry so you can switch backends without re-instrumenting.

## 09. Practices

The day-to-day disciplines that separate good engineers from great ones — version-control mastery, rigorous testing, clear process, and tool fluency compound: each discipline reinforces the others.

**What's covered:**
- **Git & version control** — distributed DVCS; three trees (working tree → index → repo) + HEAD; the content-addressed object model (blob/tree/commit/tag keyed by SHA, dedup, ~40-byte branch refs); fast-forward vs three-way merge, conflict markers; rebase (rewrites history → linear; golden rule: never rebase published commits; --force-with-lease); fetch vs pull vs push, pull --rebase; reflog rescue (~90-day safety net); git bisect (O(log n) binary search, bisect run); reset (--soft/--mixed/--hard) vs revert (safe on published branches); stash, blame, log -S, cherry-pick, tags; .gitignore only affects untracked files (git rm --cached).
- **Testing** — FIRST (Fast/Isolated/Repeatable/Self-validating/Timely), behavior not implementation; AAA (Arrange-Act-Assert); five test doubles (dummy/stub/spy/mock/fake — stubs verify state, mocks verify interaction, avoid over-mocking); the test pyramid (many unit → some integration → few E2E) vs the ice-cream-cone / hourglass anti-patterns; TDD red-green-refactor; BDD Given/When/Then (Gherkin); consumer-driven contract testing (Pact catches breaking API changes pre-deploy); Playwright (role/testid selectors, auto-wait); performance testing (load / stress / spike / soak, percentiles, k6).
- **SDLC & code quality** — Waterfall vs Agile; Scrum (sprints; PO/SM/dev roles; ceremonies; velocity-as-target pitfall) vs Kanban (WIP limits, "stop starting, start finishing," cumulative flow diagram); code review (PR size is the biggest lever — aim < 200–400 lines; blocking/nit/question/praise prefixes); static analysis (linters, formatters, type-checkers, SAST via pre-commit); code smells + behavior-preserving refactoring (tests as the safety net); technical debt (Fowler quadrant, make it visible, Boy Scout Rule, prefer Strangler Fig over a big rewrite); ADRs (immutable, superseded not edited); blameless postmortems + 5 Whys; SCA/CVEs (fail CI on high/critical); SBI feedback, estimation as ranges, stakeholder translation.
- **Regex & text processing** — literals/metacharacters/character-classes/anchors (\b word boundary is zero-width); greedy vs lazy vs possessive/atomic quantifiers; capturing / non-capturing / named groups, backreferences, alternation; lookahead/lookbehind (zero-width — e.g. a password rule with stacked positive lookaheads); flags i/g/m/s/x/u; DFA (linear, RE2/Rust/Go, ReDoS-immune) vs NFA/backtracking (rich but exponential); catastrophic backtracking / ReDoS ((a+)+$) and prevention; regex for lexing not nested parsing (never parse HTML/JSON with it); grep/ripgrep/sed/awk pipelines.

**Key mental models:** "Lost" work in Git is rarely gone — if it was ever committed, the reflog knows the hash; merge on shared branches, rebase only local history. Push coverage as low as possible (a unit bug costs seconds to localize, an E2E bug costs hours), and a flaky test is worse than no test. PR size is the single biggest lever on review quality — a 50-line PR gets read, a 2,000-line PR gets rubber-stamped. Make work and debt visible, small, and learnable; blameless postmortems fix the system, not the person.

## 10. Advanced

Cutting-edge and specialized areas where senior generalists differentiate themselves — LLM integration, data pipelines, frontend/search performance, and emerging runtimes.

**What's covered:**
- **AI & LLM integration** — the LLM as a stateless function of its context window; prompt engineering (system prompts, zero/one/few-shot, chain-of-thought, structured/JSON output); context engineering ("lost in the middle," prioritize/summarize/compact, RAG vs long context); the RAG pipeline (chunk 200–800 tokens + 10–20% overlap → embed → vector DB → ANN retrieve → cross-encoder re-rank → grounded generation with citations); embeddings + cosine similarity; vector DBs (pgvector/Pinecone/Qdrant) + HNSW ANN (multi-layer graph, tune M and ef); API knobs (token cost, temperature 0 for factual, streaming, 429 backoff, prompt caching); evaluation (golden eval sets, LLM-as-judge calibrated to humans, RAG faithfulness / context precision-recall); hallucination mitigation (ground → cite → allow "I don't know" → verify with code); prompt-injection defense (isolate user content as data, never as instructions).
- **Data engineering** — trades freshness / per-record latency for throughput / cheap aggregation; OLTP (row store) vs OLAP (columnar — less I/O, 5–10× compression, vectorized SIMD); warehouse (schema-on-write) vs lake (schema-on-read → "data swamp") vs lakehouse (Delta/Iceberg/Hudi table format = ACID over cheap files); ETL vs ELT (dbt-driven, the modern cloud default); batch (Spark) vs stream (Flink/Kafka Streams: state, event-time, delivery semantics); Lambda (dual codebase) vs Kappa (single replayable log) architectures; CDC/Debezium tails the WAL vs polling SELECT *; star schema (fact + dimensions), SCD Type 2 (valid_from/valid_to/is_current); Parquet (columnar, predicate pushdown) vs Avro (row, schema evolution); partitioning/bucketing/small-file compaction/skew (salting); orchestration DAGs (Airflow/Dagster, idempotency, backfills); data quality/lineage/governance.
- **Frontend & search** — the critical rendering path (DOM + CSSOM → render tree → layout/reflow → paint → composite; transform/opacity animate on the compositor; layout thrashing); the browser event loop (one macrotask → drain all microtasks → rAF/render); ESM/bundling (tree-shaking, code-splitting), async vs defer scripts; rendering strategies (CSR/SSR/SSG/ISR/streaming-RSC, hydration); Core Web Vitals (LCP < 2.5s, INP < 200ms, CLS < 0.1); browser storage (never tokens in localStorage), service workers/PWA; accessibility (WCAG POUR, AA target, 4.5:1 contrast, first rule of ARIA = use native HTML); the inverted index + postings-list intersection; text analysis (tokenize/normalize/stop-words/stem/edge-n-grams); TF-IDF and BM25 (saturation k1, length-norm b); Elasticsearch/Lucene (shards, mappings text vs keyword, search_after deep paging); vector/semantic search + hybrid (BM25 + vectors fused with RRF).
- **Emerging tech** — WebAssembly (portable binary stack-machine, near-native speed, linear-memory sandbox; browser compute cores + server-side WASI capability-security; Wasm vs containers = µs startup, KB–MB, deny-by-default); edge computing (latency floor from speed-of-light, V8 isolates ~5ms cold start / thousands per process vs containers, good vs poor workload fits, CDN vs edge vs central layering); FinOps (Inform → Optimize → Operate; tagging, rightsizing, reserved vs spot); green engineering (carbon-aware temporal/spatial shifting, PUE, SCI = ((E × I) + M) ÷ R, which excludes offsets); programming paradigms (imperative/OOP vs declarative/FP, composition over inheritance, pure functions + immutability, memory-management and concurrency models).

**Key mental models:** RAG scales to huge/fresh corpora far more cheaply than stuffing a giant context — and grounding + citations + "I don't know" + code verification is the durable hallucination defense (no single technique suffices). Columnar storage wins analytics for three compounding reasons (less I/O, compression, vectorization) — pick OLTP for the app, OLAP for analytics, CDC (not SELECT *) to sync them. Hybrid search (BM25 + vectors via RRF) beats either alone — keyword nails exact terms/IDs, vectors catch synonyms/intent. Wasm and V8 isolates win where you need fast startup, tiny footprint, and strong sandboxing (edge, plugins), not as a wholesale container replacement — and cost and carbon are largely the same optimization.

## Cross-Cutting Mental Models

A handful of principles recur in every section — internalize these and most specific decisions follow.

1. **Drive from requirements → numbers → justified trade-offs.** Every NFR must be a number with a condition ("p99 < 300ms at 1,000 rps," not "fast"). Clarify, estimate with back-of-envelope math, then let the numbers pick the design — and name the cost of each choice (SQL vs NoSQL, strong vs eventual, sync vs async).
2. **There is no free lunch — everything is a trade-off.** CAP (C vs A during a partition), PACELC (latency vs consistency otherwise), freshness vs speed (caching, OLAP, edge), availability vs cost (each extra nine ≈ exponential). Seniority is naming which axis you are trading and why.
3. **Assume failure, latency, and change are constant.** Networks partition, the speed of light is fixed, dependencies degrade, and requirements shift — so design for it: redundancy, retries + backoff + jitter, circuit breakers, idempotency, at-least-once + idempotent consumers, graceful degradation, and low MTTR over merely high MTBF.
4. **Start simple; add complexity only when a proven need forces it.** Modular monolith before microservices, relational before NoSQL, vertical before horizontal, long-context before RAG, KISS/YAGNI over speculative generality. Every abstraction, service, shard, and cache is a permanent operational cost.
5. **Make everything visible, small, and reversible.** Structured logs + metrics + traces for systems; small PRs, small batches, feature flags, immutable artifacts, and expand/contract migrations for delivery; error budgets, DORA metrics, and blameless postmortems for the team. You can only improve — or safely roll back — what you can see.
